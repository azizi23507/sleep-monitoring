1. INTRODUCTION: THE PHYSIOLOGICAL PROBLEM

Sleep disorders affect approximately 50-70 million adults in the United States alone, with poor sleep quality contributing to serious health conditions including cardiovascular disease, diabetes, obesity, and mental health disorders. From a deployment perspective, the physiological problem extends to accessibility: medical-grade sleep monitoring systems are confined to clinical settings, preventing continuous home-based monitoring that could provide more representative data.

The deployment challenge our project addresses:
• Clinical systems require specialized IT infrastructure and maintenance
• Complex multi-component systems (sensors, databases, applications) are difficult to deploy
• Manual configuration leads to inconsistent environments and deployment failures
• Lack of automated testing allows bugs to reach production

Our solution provides:
• One-command deployment using Docker containerization
• Automated testing and validation via CI/CD pipeline
• Consistent environments from development to production
• Reproducible builds ensuring reliable system behavior

This DevOps approach democratizes sleep monitoring technology, enabling deployment on consumer hardware without specialized IT knowledge, while maintaining production-grade reliability through automated testing and monitoring.

2. TECHNICAL SOLUTION AND ARCHITECTURE

2.1 Containerization Strategy

Docker Architecture:

The system uses a multi-container architecture orchestrated by Docker Compose:

1. PostgreSQL Container (postgres:15-alpine)
   • Persistent data storage for sensor readings and analysis results
   • Volume mounting for data persistence across container restarts
   • Health checks ensuring database availability before application start

2. Redis Container (redis:7-alpine)
   • In-memory cache for real-time data streaming
   • Circular buffer implementation (last 100 readings)
   • Automatic restart on failure

3. Backend Container (Custom multi-stage build)
   • Rust application binary
   • Python ML script and dependencies
   • Frontend static files (HTML, CSS, JavaScript)
   • Combined approach reduces container count and complexity

Container Benefits:
• Isolation: Each service runs in isolated environment
• Portability: Runs identically on any Docker-capable system
• Reproducibility: Same image produces identical behavior
• Resource Efficiency: Minimal overhead compared to VMs

2.2 Multi-Stage Docker Build

Dockerfile Architecture:

Stage 1: Builder (rust:latest)
• Install Rust toolchain and dependencies
• Compile application with optimizations
• Generate optimized release binary
• Result: ~2GB builder image (discarded)

Stage 2: Runtime (debian:bookworm-slim)
• Install minimal runtime dependencies (libpq, Python)
• Copy only compiled binary from builder
• Copy frontend files and ML scripts
• Install Python packages (pandas, scikit-learn, psycopg2)
• Result: ~400MB final image (80% size reduction)

Benefits of Multi-Stage Build:
• Security: No build tools in production image
• Performance: Smaller images = faster deployment
• Optimization: Release builds with all optimizations enabled

2.3 Docker Compose Orchestration

Service Configuration:

version: '3.8'

services:
  postgres:
    image: postgres:15-alpine
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: password
      POSTGRES_DB: sleep_monitor
    ports: ["5432:5432"]
    volumes: [postgres_data:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      
  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      
  backend:
    build:
      context: .
      dockerfile: Dockerfile
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://postgres:password@postgres:5432/sleep_monitor
      REDIS_URL: redis://redis:6379
      DB_HOST: postgres
    depends_on:
      postgres: {condition: service_healthy}
      redis: {condition: service_healthy}

Key Design Decisions:

1. Hardcoded Credentials: Development convenience, one-command deployment
2. Service Dependencies: Backend waits for healthy databases before starting
3. Network Isolation: Services communicate via Docker network (not localhost)
4. Volume Persistence: Database survives container recreation
5. Port Mapping: Expose services for external access

2.4 CI/CD Pipeline Architecture

GitHub Actions Workflow:

The automated pipeline consists of three parallel jobs:

Job 1: Test Suite
• Setup PostgreSQL and Redis services in CI environment
• Install Rust toolchain with caching
• Run database migrations
• Execute unit tests (42 tests)
• Execute integration tests with live databases
• Code quality checks (rustfmt, clippy)
• Duration: ~6 minutes

Job 2: Security Scanning
• Install cargo-audit for Rust dependency scanning
• Scan for known vulnerabilities in dependencies
• Run Trivy filesystem scanner for container vulnerabilities
• Upload results to GitHub Security tab
• Continue on non-critical findings
• Duration: ~4 minutes

Job 3: Docker Build Validation
• Set up Docker Buildx for advanced build features
• Build complete Docker image
• Validate image builds successfully
• Cache layers for faster subsequent builds
• Duration: ~8 minutes

Pipeline Triggers:
• Push to main branch: Full pipeline execution
• Pull requests: Full pipeline execution with required passing status
• Manual workflow dispatch: On-demand testing

2.6 Security Scanning Implementation

Vulnerability Detection:

cargo-audit:
• Scans Cargo.lock for dependencies with known CVEs
• Checks against RustSec Advisory Database
• Identifies outdated dependencies with security patches
• Result: Zero high/critical vulnerabilities

Trivy Scanner:
• Filesystem scanning for secrets, misconfigurations
• Container image scanning for OS vulnerabilities
• SARIF output format for GitHub Security integration
• Scans: Rust dependencies, Python packages, Debian base image
• Result: 3 low-severity findings (acceptable for development)

Security Reporting:
• Results uploaded to GitHub Security tab
• CodeQL integration for code analysis
• Automated alerts on new vulnerabilities
• Dependabot integration for dependency updates

Individual Challenges

1. Multi-Stage Docker Build Complexity (Week 2)
Challenge: Initial Dockerfile was 2GB, took 15 minutes to build
Solution: Implemented multi-stage build, separating builder from runtime image
Outcome: 80% size reduction (400MB), 60% faster builds (6 minutes)

2. CI/CD Database Connection Issues (Week 3)
Challenge: Tests failed with "database does not exist" despite migration step
Solution: Database creation was racing with migration; added explicit create step
Outcome: 100% reliable test execution with proper ordering

3. Build Caching Strategy (Week 4)
Challenge: Every build downloaded all dependencies, wasting 5 minutes
Solution: Implemented GitHub Actions cache for Rust cargo registry and Docker layers
Outcome: 50% faster builds on cache hits, reduced GitHub Actions minutes

4. Docker Build Context Path Confusion (Week 5)
Challenge: Backend Dockerfile couldn't find frontend files (different directories)
Solution: Changed build context from ./backend to . (project root), adjusted paths
Outcome: Single Dockerfile builds entire application successfully

5. Hardcoded Credentials vs. Security (Week 6)
Challenge: Security scanners flagged hardcoded database passwords
Solution: Added comments explaining development-only intent, documented production changes needed
Outcome: Balanced ease of use with security awareness
